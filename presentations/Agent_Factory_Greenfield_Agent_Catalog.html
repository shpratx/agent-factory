L1-vision-idea-intake
Takes a raw idea — free-text brief, or a reference to an existing Confluence page — and structures it into a clear problem statement, target user definition, and a set of candidate success metrics. This is the entry point of the pipeline: every downstream agent (market analysis, regulatory feasibility, vision synthesis) depends on this agent producing the same structured starting facts, so each of them reasons from a shared, consistent foundation rather than independently re-interpreting the raw idea text and drifting apart.

Inputs

Raw idea brief (free text); sponsoring stakeholder list (optional)
Human: Product Lead submission via intake form or Confluence "Idea Brief" page
External: stakeholder registry (org directory / HRIS export)

L1-vision-market-analyzer
Given the problem statement and target users already structured by the idea intake agent, builds a competitor matrix and a SWOT analysis for the proposed idea, drawing on live web search and prior competitor-profile knowledge. No idea should reach a funding decision without an honest answer to "who else already solves this" — this agent makes that check mandatory and consistent for every idea entering the pipeline, rather than something a Product Lead may or may not remember to do.

Inputs

Problem statement + target market (from idea brief); known competitor list (optional)
Agent: idea-brief.md from idea-intake

L1-vision-regulatory-feasibility-checker
Assesses the regulatory feasibility of the proposed idea against the licensing and compliance regimes relevant to its target geography and product category, classifying each constraint Green/Amber/Red with a citation and, where needed, a mitigation approach. This has to surface before roadmap commitment, not after — a viable-looking idea can be dead on arrival for regulatory reasons — and the agent runs under a zero-tolerance rule for omitting a Red-classified constraint, since a false negative here is a compliance risk, not a minor quality slip.

Inputs

Problem statement + target geography/product category (from idea brief)
Agent: idea-brief.md from idea-intake
External: regulatory database/API lookup

L1-vision-statement-generator
Synthesizes the idea brief, market analysis, and regulatory feasibility assessment — plus the viability score computed at the regulatory-feasibility quality gate — into one reconciled vision statement and roadmap outline. Three separate analyses aren't yet a decision; the Product Lead needs a single document carrying a north-star metric and a roadmap outline to approve or reject, and this agent is also the last automated checkpoint that could catch a dropped regulatory finding before it reaches a human reviewer. It produces the vision.md artifact only — publishing it to Confluence is a separate Utility agent's job (L1-confluence-publisher), per the framework's Core/Utility split.

L1-requirements-elicitor
Converts an approved vision statement into a structured set of atomic, traceable functional requirements, refusing to run unless a recorded Product Lead approval comment accompanies the vision. As the first agent to run once a vision is approved, every downstream step — NFR classification, PRD composition, impact assessment, dependency mapping, and even story generation — depends on this same atomic, traceable requirement set; without it, each downstream agent would re-interpret vision.md independently and drift from a common understanding of scope.

Inputs

Human: Product Lead approval comment (Confluence comment / Jira field)

L1-requirements-nfr-classifier
Classifies every functional requirement's non-functional boundary conditions across the six standard NFR categories — performance, security, scalability, availability, compliance, usability — citing a grounded source for each real number or rule, and honestly marking a boundary condition TBD when no source actually resolves it. Both the PRD composer and the downstream HLD agent need every requirement's cross-functional constraints resolved to a real, checkable source rather than a guess; a fabricated performance or availability number discovered at design time is far more expensive to fix than one caught here, and this agent is the single point where that classification happens once, consistently, instead of every downstream agent guessing independently.

Inputs

Functional requirements list; source regulatory feasibility assessment
Agent: requirements.md from requirements-elicitor; regulatory-feasibility.md from the regulatory-feasibility-checker (cited directly, not a KB)

Outputs

nfr-spec.md

L1-requirements-prd-composer
Composes the functional requirements and NFR spec into one authoritative PRD, carrying every requirement forward together with its cross-functional constraints in a single place instead of two documents a reader must cross-reference by hand, and folds forward Assumptions/Constraints/Risks from the vision statement. Impact assessment and dependency mapping both need one composed source of truth rather than fetching and cross-referencing requirements.md and nfr-spec.md separately, and this agent is also the last automated checkpoint that could silently drop a requirement or an NFR boundary condition between elicitation/classification and downstream planning — zero-drop composition is the concrete test it's held to, not just formatting.

Inputs

Agent: requirements.md, nfr-spec.md, and vision.md (read-only, carry-forward only)

L1-planning-impact-assessor
Assesses a PRD's blast-radius impact against the existing enterprise estate through a service-catalog capability-duplication check, a CMDB configuration-item technical-touch check, and a cross-reference of both against enterprise-architecture narrative for why. Downstream planning (dependency mapping, backlog prioritization) needs to know what a new product duplicates, touches, or newly depends on before effort is committed — a greenfield product is very often built within an already-established parent enterprise rather than in true isolation, so wherever a real service catalog and CMDB exist, this check is genuinely load-bearing, not a rubber stamp, and any mismatch between what the CMDB shows and what the architecture KB claims is surfaced as a finding rather than silently resolved.

L1-planning-dependency-mapper
Builds a dependency graph across the components and external dependencies identified in the impact assessment and PRD, independently computing — never just asserting — a cycle check and a critical path over the resulting graph. The backlog prioritizer downstream needs a topological-sort-ready graph, and the downstream HLD agent needs to know the real build-order constraints, not a hand-wave; a schema-valid graph with a reversed edge or an unverified cycle claim would pass every structural check and still be wrong, which is exactly why this agent runs the actual traversal instead of just assembling the graph's shape.

Inputs

Impact assessment; PRD
Agent: outputs of impact-assessor, prd-composer

Outputs

Tools: —Knowledge Bases: kb-L1-enterprise-architectureGuardrails: gr-L1-output-schema-validator (rejects cyclic graphs)
L1-planning-backlog-prioritizer
Prioritizes the backlog of proposed work by business value, implementation effort, and dependency risk, combining the dependency graph's build-order constraints with requirements context and Product-Lead-supplied value-scoring inputs (e.g. RICE or WSJF fields). The output is meant to be usable directly as topological-sort input further downstream, so a requirement's position in the prioritized backlog respects both its actual value and what the dependency graph says must be built before it.

Inputs

Agent: outputs of dependency-mapper, requirements-elicitor

L1-github-orchestrator
The GitHub orchestrator is one agent invoked at three distinct points across the pipeline rather than three separate agents — it doesn't generate content itself, it faithfully materializes what upstream generator agents already decided into GitHub and, where relevant, Confluence. Its design-publish invocation commits all design documents to a design branch and publishes the same set to Confluence, so the design work leaves behind both a version-controlled record and a human-readable one. Its impl-commit invocation commits API code, UI code, unit tests, and docs to the implementation branch. Its PR invocation opens the pull request that bundles the Jira, design, code, and test references together.

L1-quality-verifier
Provides independent, rubric-based scoring at every one of the 18 quality gates across the entire lifecycle, taking the draft output of whichever agent just ran together with that gate's specific rubric, and returning a quality score, a pass/fail verdict, and a rationale. It never re-fetches its own inputs — it scores exactly the draft artifact already sitting in workflow context — and it is the mechanism by which a blocking quality gate can actually stop a workflow, rather than relying on each generator agent grading its own work.

Inputs

Draft output of the agent being scored, plus the rubric for that gate
Agent: the draft artifact from whichever agent just ran (workflow context, not re-fetched)

Outputs
