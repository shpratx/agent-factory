Agent Factory · Greenfield · Phase 4 Design

L1-design-api-spec

Derives the OpenAPI contract from the functional requirements and their NFR boundary conditions — the hub artifact the LLD, test and construction agents build on.

Design doc only Exists: README.md and this blueprint. Not yet: spec.yaml, output_schema.json, instructions.md, examples/, golden/.

The agent in context

Inputs

Both documents are read from blob storage by tool-L1-azure-blob-reader, which takes a folder_name prefix and returns the decoded contents of every file under it. Either one missing is a fail-fast INSUFFICIENT_CONTEXT; the two are then cross-checked against each other before anything is derived.

DocumentProduced byCarriesStatus
requirements.md L1-requirements-elicitor functional_requirements[] — FR-NNN id, full verbatim statement, and traces_to. Its schema guarantees exact wording survives for downstream derivation, not a gloss Built
nfr-spec.md L1-requirements-nfr-classifier Per-FR boundary conditions across six categories, same ids and same order, each cited to a real source or marked TBD Built

The zero-drop check lives in this agent

L1-requirements-prd-composer is not part of this pipeline, so the two source documents are read directly rather than pre-composed. That costs one guarantee: the composer's own gate used to verify no requirement or boundary condition was lost between elicitation and design. This agent has to assert it instead — the FR-NNN set in nfr-spec.md must match requirements.md exactly, same ids and same order, before any endpoint is derived. The classifier's schema already mandates that alignment, so it is a cheap assertion rather than new analysis, but it must be an explicit step: a mismatch means an upstream agent drifted, and deriving a contract from a partial set is exactly the failure this pipeline exists to prevent.

Read access only — no writer tool is attached. This follows the Core/Utility split the other Phase 0 and Phase 1 agents use: thinking agents produce artifacts, orchestrators perform side effects. openapi.yaml reaches GitHub and Confluence at step 7 of the design workflow, when L1-github-orchestrator picks up the whole design set. Nothing this agent does is externally visible until then, which keeps a failed run cheap to discard.

Why there is no food-domain KB

A food-domain vocabulary KB — GTIN product identity, batch and lot code formats, the EU FIC 14-allergen enum, temperature-chain units, catch-weight — was planned and then dropped, because none of it is exercised by a single HarvestLink requirement. HarvestLink is a compliance and facilitation platform: FR-006 states it never takes possession, title or custody, so there is no custody chain to model and no cold-chain telemetry to represent. FR-004 is the trap — it says "allergen," but read closely it governs the declaration workflow (producer attestation, sign-off), not the allergen content. The contract needs declarationId, attestedBy, signedOffAt, status. It never needs to know what an allergen is.

What the contract genuinely needs comes from the requirements themselves, not a KB: what a compliance-documentation completeness score is and how it is bounded; that FR-003's "immutable, append-only" forbids PUT and DELETE on traceability records; that FR-006 forbids any endpoint implying HarvestLink is a transacting party. Shipping with only the two L1 KBs matches the call L1-requirements-prd-composer made when it shipped with an empty KB list. If HarvestLink later grows a real product catalogue with SKUs and cold-chain tracking, the vocabulary need appears then — building for it now would be speculative.

Processing order

1
Read both documents from blob storage
Call tool-L1-azure-blob-reader once per folder_name prefix to fetch requirements.md and nfr-spec.md.
HALT · INSUFFICIENT_CONTEXT if either is absent or unreadable
2
Assert the two inputs agree
The FR-NNN set in nfr-spec.md must match requirements.md exactly — same ids, same order. This replaces the zero-drop guarantee the PRD composer used to provide.
HALT · a mismatch means an upstream agent drifted; never derive from a partial set
3
Derive the resource model
For each FR-NNN, read its verbatim statement and identify the resource and actions it implies. One FR may yield several endpoints; each endpoint records the FR that motivated it in fr_trace.
4
Apply the NFR boundary conditions
Attach each FR's boundary conditions to the part of the contract they govern — security scheme, documented rate limit, error response shape, pagination. Each attachment is recorded in nfr_trace with what it shaped.
A TBD is carried through as an open question, never resolved into a plausible number
5
Apply the enterprise constraints
Every route is gateway-published and independently deployable — no point-to-point call into a legacy system, no write-back to SMDS or SAP ERP. External-facing operations carry the external identity provider's scheme, never Azure AD, and every limit is enforced server-side.
6
Self-check both directions
Every FR-NNN maps to at least one endpoint or is explicitly marked non_api with a reason; every endpoint traces back to a real FR-NNN. No orphans either way.
7
Emit
openapi.yaml as valid OpenAPI 3.x, plus the structured items[] mirror above. Unresolved boundary conditions appear as x-open-question extensions on the paths they affect.
