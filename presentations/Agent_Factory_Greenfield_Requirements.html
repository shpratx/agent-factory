Agent Factory Reference — Greenfield Extension

Agent Requirements Spec — Functional & Non-Functional

Developer starting spec for all 34 agents. Read alongside Agent_Factory_E2E_SDLC_Diagram_Greenfield.html (topology) and Agent_Factory_Greenfield_BOM.html (inputs/outputs/tools/KBs) — this document defines what "done" means for each one.

Global NFR Baseline — Applies to Every Agent

Per-agent sections below list only deltas from this baseline. If an agent has no delta, it inherits these unchanged.

IDCategoryRequirement
NFR-G1Single ResponsibilityAgent performs exactly one function. Must reject or flag requests outside its declared scope rather than silently expanding it.
NFR-G2StatelessnessNo retained state between invocations. All context arrives via the input payload and KB retrieval for that call only.
NFR-G3Structured OutputOutput conforms to a published JSON Schema or Markdown template. Malformed output fails gr-L1-output-schema-validator and is rejected before downstream use.
NFR-G4Explicit FailureOn insufficient input, return a structured error stating which required input was missing or ambiguous — never a best-effort hallucinated partial answer.
NFR-G5GroundingEvery domain-specific claim must be grounded in a retrieved KB chunk or a provided input. No reliance on model training data for org-specific facts.
NFR-G6Latency (default)P95 ≤ 15s for markdown/JSON drafting agents. Code-generation and diagram-heavy agents override this individually below.
NFR-G7Idempotency & RetryRe-running with identical input yields an equivalent output. Tool-calling agents check-before-create. Workflow retries max 2 (exponential backoff) before escalating to HITL.
NFR-G8ObservabilityEmit start/complete/error events tagged with the workflow correlation ID. Log input hash, output hash, token usage, model version, KB version, guardrail results.
NFR-G9Security & SecretsNever accept, log, or echo raw credentials/tokens. Any secret a tool call needs is injected via SecretsSDK at call time, never embedded in prompt or output.
NFR-G10Versioning & LayeringDefined so L2/L3/L4 variants extend it via instructions_append/knowledge_bases_append without modifying the L1 baseline. Breaking changes require a semver major bump and regression testing across dependent layers.
NFR-G11Guardrail EnforcementEvery guardrail listed for this agent in the BOM runs synchronously before output is released. A guardrail failure blocks release and raises an HITL escalation event.
NFR-G12Quality-Gate ComplianceOutput must be deterministically scorable by L1-quality-verifier against the agent's published rubric — expose enough structure (sections/fields) for consistent scoring.

PHASE 0 Idea → Vision

L1-vision-idea-intakeStructures a raw idea into a problem statement, target users, and success metrics.

Functional Requirements

  1. Accept a free-text idea brief (up to ~2,000 words) plus an optional stakeholder list.
  2. Extract/synthesize: problem statement, target user segment(s), value proposition, candidate success metrics.
  3. If the brief lacks a clear problem statement or target user, flag the missing field explicitly rather than inventing one.
  4. Fetch the raw brief via tool-L1-confluence-fetch-page when given a page reference instead of inline text.
  5. Output idea-brief.md conforming to the kb-L1-sdlc-templates idea-brief schema.

NFR Deltas

  • Latency: P95 ≤ 10s.
  • Any suggested success metric not directly implied by the input must be tagged "suggested — pending stakeholder validation".
L1-vision-market-analyzerCompetitor analysis and SWOT for the proposed idea.

Functional Requirements

  1. Accept idea-brief.md.
  2. Issue at least one tool-L1-web-search-competitor-scan query per identified competitor category.
  3. Produce a competitor matrix (name, positioning, strengths/weaknesses) and a SWOT grid.
  4. Every competitor claim must carry a source citation (URL + retrieval date).
  5. If search returns no relevant results, state "insufficient market data" rather than fabricate competitors.

NFR Deltas

  • Latency: P95 ≤ 30s (bounded by external search round-trip).
  • gr-L1-citation-verifier BLOCKER rejects output if any competitor claim lacks a citation.
L1-vision-regulatory-feasibility-checkerRegulatory feasibility assessment for the target market.

Functional Requirements

  1. Accept idea-brief.md (target geography, product category).
  2. Query tool-L1-regulatory-db-lookup for applicable regimes (licensing, data residency, consumer protection).
  3. Classify feasibility Green/Amber/Red per constraint, with rationale.
  4. Cite the specific regulation/section for every constraint raised.
  5. Every Amber/Red item must include a mitigation recommendation or a "requires legal review" flag.

NFR Deltas

  • Latency: P95 ≤ 30s.
  • Zero tolerance for omitting a Red-classified constraint BLOCKER — false negatives here are a compliance risk.
L1-vision-statement-generatorSynthesizes idea, market, and regulatory findings into a vision statement and roadmap outline.

Functional Requirements

  1. Accept idea brief, market analysis, regulatory feasibility, and viability score.
  2. Produce vision.md: problem, target users, value proposition, north-star metric(s), phase-level roadmap outline.
  3. Reconcile conflicts between inputs (e.g. a Red regulatory flag vs. a proposed feature) and surface them as open risks — never silently drop them.
  4. Publish via tool-L1-confluence-create-page.

NFR Deltas

  • Latency: P95 ≤ 15s.
  • Must block auto-publish if viability score <7 — return for human review instead.

PHASE 1 Requirements → Impact Assessment → Dependency Graph

L1-requirements-elicitorConverts the approved vision into structured functional requirements.

Functional Requirements

  1. Accept approved vision.md + Product Lead approval comment.
  2. Decompose vision into discrete, testable functional requirements — one requirement per atomic capability.
  3. Each requirement must trace back to a specific vision clause.
  4. Flag ambiguous or "and"-joined compound requirements for splitting rather than passing them through as-is.

NFR Deltas

  • Latency: P95 ≤ 20s.
  • Must refuse to proceed if vision.md carries no recorded human-approval comment — enforces the Phase 0→1 gate at the agent level.
L1-requirements-nfr-classifierClassifies non-functional requirements and boundary conditions.

Functional Requirements

  1. Accept requirements.md.
  2. Classify each requirement against NFR categories: performance, security, scalability, availability, compliance, usability.
  3. Define explicit boundary conditions where the input supports them (e.g. concurrency, latency); mark unsupported numeric NFRs "TBD — needs stakeholder input".
  4. Output nfr-spec.md with one section per requirement.

NFR Deltas

  • Must never emit a fabricated numeric SLA BLOCKER — any numeric NFR either traces to input or is marked TBD.
L1-planning-impact-assessorAssesses blast-radius impact of proposed requirements against existing systems (or a proposed component map for pure greenfield).

Functional Requirements

  1. Accept requirements.md + nfr-spec.md + service catalog/CMDB export (may be empty for greenfield).
  2. For each requirement, identify affected/created components and estimate blast radius (new build vs. touches existing system).
  3. Score each impact Low/Medium/High with rationale.
  4. For pure-greenfield projects, explicitly state "no existing systems affected — net-new build" rather than fabricate impacts.

NFR Deltas

  • Must degrade gracefully (not error) when the CMDB export is empty or absent.
L1-planning-dependency-mapperBuilds a dependency graph across proposed epics, services, and integrations.

Functional Requirements

  1. Accept impact-assessment.md + requirements.md.
  2. Construct a directed graph with typed edges (blocks / depends-on / integrates-with).
  3. Detect cyclic dependencies and surface the cycle explicitly — never silently drop an edge to "resolve" it.
  4. Output dependency-graph.json conforming to a published graph schema (nodes, edges, critical path).

NFR Deltas

  • gr-L1-output-schema-validator hard-fails on any cycle BLOCKER — escalate to HITL, do not auto-resolve.

PHASE 2 Project / Sprint Planning

L1-planning-backlog-prioritizerPrioritizes backlog items by value, effort, and dependency risk.

Functional Requirements

  1. Accept dependency-graph.json + requirements.md + value-scoring inputs (RICE/WSJF fields).
  2. Compute a priority ranking that respects dependency ordering — a dependent item cannot outrank its blocker.
  3. Output prioritized-backlog.md with rank, score, and one-line rationale per item.
  4. Mark an item's rank "provisional" if its value-scoring input is missing, rather than assigning a default score.

NFR Deltas

  • Output ordering must be a valid topological sort of the dependency graph — verify programmatically, not just via model judgment.
L1-planning-sprint-plannerAllocates prioritized backlog into 5-day Feature Cycles by team capacity.

Functional Requirements

  1. Accept prioritized-backlog.md + team capacity/velocity data.
  2. Allocate items into Feature Cycles without exceeding stated capacity per cycle.
  3. Flag any item that cannot fit within the visible planning horizon rather than silently overcommitting.
  4. Create/update roadmap structure in Jira via tool-L1-jira-create-issue/tool-L1-jira-update-issue.

NFR Deltas

  • Idempotent: re-running with the same backlog + capacity must not create duplicate Jira issues (check-before-create).

PHASE 3 Inception — Epics, Features, Stories, Tasks

L1-inception-epic-creatorGenerates epics from the approved roadmap and vision.

Functional Requirements

  1. Accept approved roadmap.md + vision.md.
  2. Generate one epic per roadmap Feature Cycle grouping: title, description, business-value statement, target cycle.
  3. Each epic maps to exactly one roadmap item — no merging or splitting beyond what the roadmap specifies.
  4. Check for an existing matching epic via tool-L1-jira-fetch-issue before creating a new one.

NFR Deltas

  • When domain=food-production-distribution, must satisfy gr-L2-food-domain-compliance — epics touching food-safety/traceability/allergen flows carry HACCP/Natasha's-Law scope tags.
L1-inception-feature-decomposerDecomposes epics into features.

Functional Requirements

  1. Accept epics.json.
  2. Decompose each epic into 2–8 independently shippable features (range configurable per L2/L3 extension).
  3. Each feature restates the parent epic's business value in its own scope.
  4. Reject a decomposition where a single feature would need more than one epic's worth of scope — signal for epic re-scoping instead.

NFR Deltas

None beyond baseline.

L1-inception-story-generatorGenerates user stories with acceptance criteria from features.

Functional Requirements

  1. Accept features.json + requirements.md.
  2. Generate stories in As-a/I-want/So-that format with Given/When/Then acceptance criteria.
  3. Every story traces to exactly one feature and cites the requirement(s) it satisfies.
  4. Flag stories that will need PII-shaped test data so testing-synthetic-data-generator knows to route accordingly.

NFR Deltas

  • gr-L1-pii-detection must scan illustrative example data inside acceptance criteria and block any realistic-looking PII, even in examples.
L1-inception-task-generatorDecomposes stories into engineering tasks.

Functional Requirements

  1. Accept stories.json.
  2. Decompose each story into backend/frontend/test/docs tasks sized ≤1 developer-day.
  3. Tag each task with an estimated complexity (S/M/L).

NFR Deltas

  • Quality-gate threshold is 6/10 (task-completeness), lower than the 7/10 baseline elsewhere — reflects lower blast radius of a mis-scoped task vs. a mis-scoped story.
L1-jira-orchestratorCreates epics, stories, and tasks as Jira issues (also used in Phase 2 for roadmap creation).

Functional Requirements

  1. Accept epics/features/stories/tasks JSON.
  2. Check-before-create against Jira (query by title + parent) to avoid duplicates.
  3. Preserve hierarchy links (epic→story→task) using Jira's native linking.

NFR Deltas

  • Retry on Jira 5xx/rate-limit responses (max 2, exponential backoff) before escalating to HITL.
  • Must never log or embed the Jira API token in any output artifact.

PHASE 4 Design — User Journeys, Wireframes, HLD, LLD, API Spec, Data Model

L1-design-user-journey-mapperMaps end-to-end persona journeys and touchpoints ahead of wireframing.

Functional Requirements

  1. Accept stories.json + personas from vision.md.
  2. Produce journey maps per persona: stages, touchpoints, pain points, drop-off risks.
  3. Every journey traces to the stories it exercises.

NFR Deltas

None beyond baseline.

L1-design-ux-wireframeGenerates wireframes/screen layouts from stories and journeys.

Functional Requirements

  1. Accept stories.json + user-journeys.md.
  2. Produce a component hierarchy and screen-by-screen layout per journey stage (or Figma frames, if enabled).
  3. Flag any story lacking sufficient UI detail to wireframe rather than inventing UI not implied by the story.

NFR Deltas

None beyond baseline.

L1-design-api-specGenerates the OpenAPI contract from story scope and NFRs.

Functional Requirements

  1. Accept stories.json + nfr-spec.md.
  2. Produce an OpenAPI 3.x spec: endpoints, request/response schemas, auth scheme, error codes, rate limits (from NFR spec where defined).
  3. Every endpoint traces to at least one story.
  4. Validate the generated spec against the OpenAPI JSON Schema before returning.

NFR Deltas

  • gr-L1-schema-validator failure on invalid OpenAPI syntax is build-blocking, not advisory BLOCKER.
L1-design-hldGenerates the high-level design — C4 diagrams, components, data flow, integrations.

Functional Requirements

  1. Accept requirements.md + nfr-spec.md + dependency-graph.json + openapi.yaml.
  2. Produce C4 context/container diagrams (Mermaid or PlantUML text), component responsibilities, data flow, integration points.
  3. Every integration point named must already exist in dependency-graph.json — no undeclared integrations.

NFR Deltas

  • Latency: P95 ≤ 60s (diagram generation is heavier than plain drafting).
L1-design-lldGenerates the low-level design — classes, sequence diagrams, error handling.

Functional Requirements

  1. Accept hld.md + openapi.yaml.
  2. Produce class-level design, sequence diagrams per key flow, and an error-handling strategy.
  3. Every class/module named must map to a component declared in the HLD.

NFR Deltas

None beyond baseline.

L1-design-data-architectDesigns the data model — schema, lineage, migration plan.

Functional Requirements

  1. Accept lld.md + requirements.md.
  2. Produce schema DDL, entity-relationship description, lineage notes, and an initial migration plan.
  3. Flag any field storing PII/sensitive data with the required encryption/masking approach.

NFR Deltas

  • gr-L1-pii-detection must verify no PII column is left in plaintext without a documented masking/encryption decision.
L1-github-orchestrator (design-publish invocation)Commits design documents to the design branch and publishes to Confluence.

Functional Requirements

  1. Accept all Phase 4 design outputs.
  2. Create branch aava/design-{feature-id}, commit each artifact as a separate file, mirror to Confluence pages.

NFR Deltas

  • Must not overwrite an existing branch/page without an explicit "update" flag — protects prior human edits.

PHASE 5 Test Strategy — Scenarios, Cases, Scripts, Synthetic Data

L1-testing-scenario-writerGenerates test scenarios from stories and acceptance criteria.

Functional Requirements

  1. Accept stories.json.
  2. Produce scenarios covering happy path, edge cases, and negative cases per AC clause.
  3. Minimum coverage: at least one happy-path and one negative scenario per AC clause.

NFR Deltas

None beyond baseline.

L1-testing-case-writerGenerates Cucumber Given/When/Then cases from scenarios.

Functional Requirements

  1. Accept test-scenarios.md.
  2. Produce one Cucumber case per scenario.
  3. Reuse existing step definitions where semantically identical steps already exist — avoid duplicate step libraries.

NFR Deltas

None beyond baseline.

L1-testing-script-generatorGenerates executable automation scripts (Playwright/REST Assured) from test cases.

Functional Requirements

  1. Accept test-cases.feature + openapi.yaml + wireframes.md.
  2. Generate Playwright (UI) or REST Assured (API) scripts implementing each Cucumber step.
  3. Generated scripts must compile/lint clean (0 syntax errors) before being returned.

NFR Deltas

  • Executability check BLOCKER: script must pass a dry-run/lint step, not just schema validation — stricter than baseline.
L1-testing-synthetic-data-generatorGenerates PII-safe synthetic test data and fixtures.

Functional Requirements

  1. Accept db-schema.sql + test-cases.feature.
  2. Generate fixture data matching schema types/constraints, sufficient to exercise each test case.
  3. No generated value may resemble real production PII patterns — use recognizably fake ranges/test-only values.

NFR Deltas

  • gr-L1-pii-detection is a hard release-blocker BLOCKER here, zero tolerance, no override.
L1-xray-orchestratorCreates test cases and links executable scripts in XRay.

Functional Requirements

  1. Accept test cases + automation scripts.
  2. Check-before-create against XRay to avoid duplicate entries; link each test to its parent story.

NFR Deltas

Standard retry/idempotency baseline.

PHASE 6 Construction — API Code Gen, UI Code Gen

L1-construction-api-code-generatorGenerates backend/API implementation from LLD, API spec, and data model.

Functional Requirements

  1. Accept lld.md + openapi.yaml + db-schema.sql + repo scaffold.
  2. Generate backend source implementing every endpoint in the API spec and every class in the LLD.
  3. Generated code must compile (0 build errors) and pass static analysis lint before being returned.
  4. Must not introduce any endpoint/behavior absent from the API spec — no speculative features.

NFR Deltas

  • Latency: P95 ≤ 120s per service (batchable across files).
  • gr-L1-secret-scanner and gr-L1-license-compliance-check are hard release-blockers BLOCKER.
L1-construction-ui-code-generatorGenerates frontend/UI implementation from wireframes, journeys, and API spec.

Functional Requirements

  1. Accept wireframes.md + user-journeys.md + openapi.yaml + repo scaffold.
  2. Generate frontend source implementing every screen in the wireframes, wired to the API spec's endpoints.
  3. Generated code must build (0 build errors) and pass lint before being returned.

NFR Deltas

  • Latency: P95 ≤ 120s per screen/module.
  • Same gr-L1-secret-scanner/gr-L1-license-compliance-check blockers as the API generator.
L1-construction-unit-test-generatorGenerates unit tests for both API and UI code.

Functional Requirements

  1. Accept API + UI source code.
  2. Generate unit tests achieving a minimum stated coverage target (e.g. ≥80% line coverage) per module.
  3. Tests must actually execute against the generated code, not just be schema-valid — a failing/erroring suite is a build-blocking failure.

NFR Deltas

  • Coverage threshold enforcement is part of the quality gate, not advisory.
L1-construction-code-reviewerReviews generated code for standards compliance, vulnerabilities, and refactor opportunities.

Functional Requirements

  1. Accept API + UI source code + unit tests.
  2. Flag standards violations, security vulnerabilities (OWASP Top 10 patterns), and refactor opportunities.
  3. Every flagged issue cites the specific file/line and the violated standard/rule.
  4. Classify findings by severity (blocker/major/minor); blockers halt the PR from being marked ready.

NFR Deltas

None beyond baseline.

L1-construction-doc-generatorGenerates API/code documentation and changelog.

Functional Requirements

  1. Accept API + UI source code + openapi.yaml.
  2. Generate README, API usage docs, and a changelog entry.
  3. Validate doc claims against the actual source/spec before returning — no generic boilerplate that doesn't match the code.

NFR Deltas

None beyond baseline.

L1-github-orchestrator (impl-commit invocation)Commits API code, UI code, unit tests, and docs to the implementation branch.

Functional Requirements

  1. Accept all Phase 6 outputs.
  2. Create/update branch aava/impl-{feature-id} with each artifact committed.

NFR Deltas

  • Must not overwrite an existing branch without an explicit "update" flag.

PHASE 7 PR Creation

L1-github-orchestrator (PR invocation)Creates the pull request bundling Jira, design, code, and test references.

Functional Requirements

  1. Accept impl branch, design branch, Jira issue keys, XRay test keys.
  2. Compose a PR description bundling all references (per the diagram's PR template).
  3. Check-before-create — never open a duplicate PR for the same branch pair.

NFR Deltas

  • The PR description must be human-readable without needing to open every linked system — include enough summary inline.

CROSS-CUTTING Quality Verification

L1-quality-verifierIndependent rubric-based scoring, invoked at all 18 quality gates across the lifecycle.

Functional Requirements

  1. Accept a draft artifact + its rubric ID.
  2. Score 0–10 against the rubric's dimensions; return per-dimension sub-scores, overall score, and rationale.
  3. Must be independent — never restate the generating agent's own self-assessment as the score.

NFR Deltas

  • Score stability: repeated scoring of the same artifact must vary by ≤1 point — deterministic enough to be trusted as a gate.
How to use this doc: each agent card's Functional Requirements are the acceptance criteria for a first working version. NFR deltas marked BLOCKER are non-negotiable release gates — implement the corresponding guardrail check before the agent goes anywhere near a live workflow, not as a follow-up.
