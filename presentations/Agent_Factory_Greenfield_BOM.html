Update 2026-08-31 — idea-brief is JSON, not Markdown: L1-vision-idea-intake emits idea-brief.json. The brief is not a narrative document — it is a structured record (problem statement, target users, value proposition, success metrics with stated/suggested grading, open questions, each item carrying its traced_to input excerpt), and both downstream consumers, L1-vision-market-analyzer and L1-vision-regulatory-feasibility-checker, read specific fields out of it rather than reading it end to end. A Markdown artifact forced those agents to re-parse prose to recover fields the intake agent already had structured, and put the trace links somewhere no validator could check them. As JSON the artifact is schema-validated by gr-L1-output-schema-validator directly, and the field-level traceability survives into Phase 0's later steps. The S4 note in the Knowledge Bases column still holds — the structure stays embedded in the agent's own instructions.md / output_schema.json, not paid for as a KB retrieval. Downstream artifacts (market-analysis.md, regulatory-feasibility.md, vision.md) are unchanged: those are narrative documents with a human reader at the Phase 0 gate.

Update 2026-08-05 — re-scope extended through the full pipeline: the domain seam noted above is resolved. kb-L2-payments-domain (Phases 1, 3, 5) is now kb-L2-domain-regulatory or kb-L2-food-domain depending on which agent consumes it; gr-L2-payments-compliance (Phases 1, 3) is now gr-L2-food-domain-compliance; kb-L2-payments-api-patterns (Phase 4) is now kb-L2-food-domain-api-patterns. Update 2026-08-08 — correction: "greenfield" ≠ "no parent enterprise": the 2026-08-07 entry above correctly identified that these two KBs had no real content, but incorrectly concluded that meant they should stay unbuilt. "Greenfield" describes the HarvestLink *product* — it does not mean HarvestLink has no parent *enterprise*. A new digital product built inside an already-established company (the far more common real-world case) has a real existing-systems landscape to assess impact against, and real existing security standards a new product must satisfy — that's exactly what triggers a genuine, non-trivial L1-planning-impact-assessor run rather than a rubber-stamped "no existing systems" every time. Both KBs are now built with illustrative-but-detailed content for a fictional parent enterprise, Thornbury Foods Group (a UK food wholesale/distribution conglomerate that HarvestLink is a new digital-product unit within) — see knowledge-bases/kb-L1-enterprise-architecture and knowledge-bases/kb-L1-enterprise-security at the project root (cross-phase, not scoped under any single phase-N/ directory, since Phases 1, 2, 3, 4, and 6 all reference them). phase-1/examples/impact-assessment.md was rewritten accordingly: the CMDB is no longer empty, three existing systems are genuinely touched (one read-only check, one outbound-only feed, one mandatory integration pattern), two are explicitly excluded by architecture decision rather than oversight, and checking the security KB's identity boundary surfaced a genuinely new external dependency (HarvestLink needs its own external identity provider — Thornbury's employee SSO doesn't cover producers/distributors/buyers) that wasn't visible at vision or requirements stage. Back-ported 2026-08-08: dependency-graph.json now includes the external-identity-provider node — it ties with the compliance-completeness-methodology chain for the graph's critical path (independently re-verified: no cycle introduced, longest path still 3 edges, now via two distinct roots converging on allergen-declaration-service), and nfr-spec.md/prd.md now cite the security KB to resolve 3 of their former "TBD" boundary conditions (FR-001's 6-year retention, FR-003's and FR-008's availability SLAs) instead of leaving them open — six genuine TBDs remain in each, down from nine.
Update 2026-08-09 — all 5 Phase 1 core agents + evaluators built as full reference-pattern packages: L1-requirements-elicitor, -nfr-classifier, -prd-composer, L1-planning-impact-assessor, and -dependency-mapper each now have a complete agents/<name>/ package (spec.yaml, output_schema.json, evaluation.md, README.md, examples/, golden/v1.0.0/) plus a paired -evaluator agent and a prompts/<name>/instructions.md, same S6 Generator→Evaluator pattern as Phase 0. A new gr-L1-requirements-quality-gate guardrail (7 rules: schema compliance, ID sequencing, compound-split integrity, unambiguous-vague-term scan, singular/verifiable/consistent checks) is wired into L1-requirements-elicitor-evaluator's context.guardrails, validating the RESULTANT post-fix requirements content against ISO/IEC/IEEE 29148 — see kb-L1-requirements-quality-standard (new) and guardrails/gr-L1-requirements-quality-gate/. Cross-file reconciliation caught and fixed two seams from building these in parallel before every upstream schema existed: L1-planning-impact-assessor's and -dependency-mapper's golden/example input fixtures had guessed shapes for prd_output/impact_assessment_output (e.g. bare-string narrative fields, wrong Component/ExternalDependency field names, an invented component_dependencies field that contradicts dependency-mapper's own edge-derivation design) — all now spliced from the real upstream agents' actual output_schema.json-conformant content, re-validated end to end. Separately, L1-planning-impact-assessor's prompt and spec.yaml had let the worked scenario's product/company names (HarvestLink, Thornbury Foods Group) leak into the operative BACK STORY/business_value prose instead of staying confined to examples//golden/ fixtures — genericized to "a greenfield product built within an established parent enterprise" so the agent stays domain- and organization-agnostic, consistent with every other L1 agent in this document.
