APPENDIX A Output Contract — roadmap.md (feature → band)

Produced by L1-planning-roadmap-creator · outer loop · feature granularity · whole-PI horizon

The roadmap is the multi-sprint "what and roughly when." It never descends below feature granularity — no stories, no Work Units, no per-person assignment. One row per feature; every feature in the prioritized backlog must appear exactly once.

Invariant: a feature may only be banded into a cycle at or after the cycle of every feature it depends on (per dependency-graph.json). The gr-L1-consistency-check guardrail rejects any roadmap that bands a feature earlier than one of its predecessors, or that leaves a backlog feature unplaced.

APPENDIX B Output Contract — cycle-plan.md (Work Unit → cycle)

Produced by L1-planning-feature-cycle-planner · inner loop · Work-Unit granularity · near cycle(s) only

Terminology: this contract maps Work Units (the atomic executable — the level formerly called "Task") to cycles. Where a committed feature is oversized (needs_slicing=true), Work Units hang under an optional Story slice (a sub-feature) via slice_id; otherwise they attach straight to the feature. The IDs use the WU- prefix. task-generator/tasks.json retain their names for tooling continuity — a "task" record is a Work Unit.

The cycle plan descends to the executable level: it takes the committed features from roadmap.md, triggers just-in-time Work-Unit elaboration, and fits those Work Units to team capacity for the near cycle(s). It never re-bands features — if Work Units overflow, it flags the overflow for the roadmap-creator to reflow, keeping the outer loop authoritative.

Invariant: the sum of committed unit_points in any cycle must be ≤ that cycle's capacity. gr-L1-consistency-check rejects an over-committed cycle; overflow Work Units must carry disposition=overflow with a target reflow band, not be silently dropped.

APPENDIX C Decomposition Standard — the rubric feature-decomposer & task-generator decompose against

Why this exists

The inherited Jira ladder (Epic → Feature → Story → Task) was built to solve a human coordination problem, not an agent execution problem. It conflates two things that pull in opposite directions: human governance granularity (the levels at which a human states intent, prioritizes, and approves — wants to be coarse) and agent execution granularity (the level at which an agent reliably picks up and completes work — governed by context, not effort). This standard separates the two and gives the decomposer agents a concrete, testable rubric.

Governing rule: decompose to the coarsest level at which each unit is still independently verifiable and context-bounded — and no finer. Over-decomposition is a named failure mode: units too small create coordination overhead, lose the thread of the larger goal, and burn more orchestration/tokens than they save.

C.2 — The collapsible-story rule

A user story was always two things wearing one hat: (a) a vertical slice of value, and (b) acceptance criteria in narrative form. In the ADLC these separate cleanly:

• The acceptance criteria attach directly to the Feature — agents consume Given/When/Then perfectly well without the "As a… I want…" wrapper.
• The vertical slice only needs its own level when a feature genuinely won't fit one cycle — at which point a "story" is a sub-feature.

Decision: the feature-decomposer emits a needs_slicing flag. If a feature passes the "fits one cycle" test, no story layer is created and story-generator elaborates Work Units straight from the feature's AC. If it fails, the decomposer emits Story (sub-feature) rows first, each of which independently re-runs the same fit test.

C.3 — The five right-sizing tests (encodable guardrails)

These are the checks a Work Unit must pass to be considered well-formed. They are encoded as a guardrail, gr-L1-decomposition-rightsizing, run by both feature-decomposer (on each feature/sub-feature) and task-generator (on each Work Unit). Each test maps to a machine-checkable rule so the guardrail can BLOCK, not just advise.

#TestWhat it meansEncoded check (rule)Verdict on fail
T1One coherent thing per sessionA single, nameable objective — no hidden second job.title contains no coordinating conjunction ("and"/"&"/","-joined verbs); exactly one primary verb + one object. Regex + POS check on the unit title/description.BLOCK → split
T2Context-boundedThe agent can read what it needs without ingesting the whole codebase.est_files_read ≤ N (default 12) AND est_context_tokens ≤ 0.5 × model_window. Count files read, not files changed.BLOCK → split
T3Independently verifiableIt has its own pass/fail check that doesn't depend on downstream interpretation.verification_ref is non-empty and resolves to a concrete test/assertion/acceptance-criterion ID. No unit ships without a named verifier.BLOCK → add verifier
T4Layer-alignedCuts fall on natural seams (DB → API → UI → integration → test).layer ∈ {data, api, business-logic, ui, integration, test, docs}; a unit spanning >1 layer is flagged as a split candidate.WARN → prefer split
T5Not over-splitA unit that only makes sense alongside 5 siblings is too small.hard_dependency_count on sibling units ≤ 2; if a unit is unverifiable in isolation (T3 fails because it needs siblings), merge upward.WARN → merge
Guardrail wiring: gr-L1-decomposition-rightsizing is added to L1-inception-feature-decomposer's context.guardrails (validating each feature/sub-feature against T1–T5, using T2 with the feature's rough size as the estimate) and to L1-inception-task-generator's context.guardrails (validating each Work Unit). T1–T3 are BLOCKERS (a failing unit cannot be emitted — the agent must split or add a verifier and re-run); T4–T5 are WARN-level (surfaced in reflection_notes for the evaluator, split/merge preferred but not forced, since some layer-spanning or tightly-coupled units are legitimate). Supporting taxonomy lives in kb-L1-decomposition-standard (the 3-level spine, the collapsible-story rule, the layer enum, and the default thresholds N=12 / 0.5×window — all overridable per L2/L3 domain variant via knowledge_bases_append).

APPENDIX D Applying the Standard in Practice — from work request to Jira

This appendix shows how the rules in Appendix C are executed the moment a work request lands, and exactly how each level materialises as Jira issues. The through-line: a human states intent, the pipeline classifies and decomposes to the right depth, and L1-jira-orchestrator writes the resulting hierarchy into Jira with the fields and gates that let agents pick work up autonomously.

D.1 — Step 0: intake & work-type classification

Every request enters through one door — a Confluence "request" page or a Jira intake ticket — carrying a single decisive tag: work_type ∈ { greenfield | brownfield | bugfix }. This tag selects the decomposition profile (Appendix C.4) and therefore how many levels get created. If the requester doesn't set it, L1-inception-epic-creator (greenfield/brownfield) or a lightweight triage step (bugfix) infers it from the request and the impact scan, and the inferred value is confirmed at the first human gate.
