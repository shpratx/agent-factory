1. Purpose & Scope

In scope

  • Read an approved roadmap and a vision statement, and produce a complete, non-overlapping set of epics.
  • Attach traceability (each epic → roadmap line + vision theme).
  • Surface gaps or ambiguity explicitly as open_questions rather than guessing.
  • Check for duplicate epics already in Jira before proposing new ones.

Out of scope (deliberately)

  • Decomposing epics into features/stories/tasks — that's A2/A3/A4.
  • Creating Jira issues — that's jira-orchestrator.
  • Re-validating or re-approving the roadmap itself — the Product Lead sign-off is a precondition, not this agent's job.
  • Scoring its own output — that's A12 Verifier, deliberately a separate context.

Single-responsibility statement: "Given an approved roadmap and vision, and nothing else, produce the epic backlog that roadmap implies — one epic set, fully traceable, with no invented scope." Everything below exists to make that statement actually hold under real, messy inputs.

Design consideration — don't trust "approved" as a label alone. If roadmap.md and vision.md disagree (e.g., roadmap references a capability not in vision, or vice versa), that's a real signal something upstream drifted. The agent should treat this as an open_question, not silently pick one source as authoritative.

5. Reasoning Pattern — Reflection + Grounding

Two patterns, each solving a different failure mode:

Grounding — solves hallucinated scope

Without grounding, an LLM asked "generate epics from this roadmap" will happily fill gaps with plausible-sounding but invented capabilities, because that's what makes a fluent-sounding epic. The grounding rule forces every field to cite a specific source line — if it can't, the field doesn't get written, it becomes an open_question.

Reflection — solves structural errors within an otherwise-grounded draft

Grounding alone doesn't catch cross-epic problems: two epics covering the same roadmap item, a roadmap item nothing covers, or an epic scoped across two roadmap phases. Those require looking at the whole draft set at once, which is exactly what a reflection pass does that single-pass grounding can't.

1Ground — map roadmap items + vision themes to candidate epics before writing prose.
→
2Dedupe check — call tool-L1-jira-fetch-issue, compare candidates against existing epics.
→
3Draft — write full epic objects with source_refs.
→
4Reflect — run the 5-point checklist below against the full set.
→
5Emit — finalize epics.json.

Reflection checklist (step 4)

  1. Does every epic map to at least one roadmap item? (no orphans)
  2. Does every roadmap item map to at least one epic? (no coverage gaps)
  3. Any duplicate or overlapping epics that should merge?
  4. Any epic whose scope spans more than one roadmap phase? (split candidate — flag, don't silently split)
  5. Any PII, credentials, or customer-identifying content leaking into a description?

6. Prompt Architecture

# SYSTEM
Role: L1-inception-epic-creator. Single responsibility: convert an
approved roadmap + vision into an epic backlog. Do not decompose into
features/stories/tasks — out of scope (NFR-G1).

Grounding rule: every epic field must cite its source as
roadmap:<line-id>, vision:<section-id>, or kb:<template-id>.
Never rely on general domain knowledge for org-specific claims (NFR-G5).
If a plausible epic has no traceable source, do not write it — record
it in `open_questions` instead.

Output contract: return ONLY valid JSON matching <epics.schema.json>.
No markdown fencing, no commentary before or after the array.

On missing/ambiguous roadmap or vision input, or on a Product-Lead
approval flag that is absent/false: return a structured error naming
the missing precondition (NFR-G4) — do not proceed.

# STEP 1 — GROUND
Map each roadmap line item to a vision theme it supports. Where no
supporting vision theme exists, flag the mismatch instead of proceeding.

# STEP 2 — DEDUPE
Call tool-L1-jira-fetch-issue for existing epics in this project.
Compare candidate epics against them by title/description similarity.
Record findings in `dedupe_check`, even if empty.

# STEP 3 — DRAFT (internal)
For each grounded roadmap/vision pairing, write a candidate epic:
title, description, business_value, priority, target_phase, source_refs.

# STEP 4 — REFLECT (internal, not returned to caller)
Re-read the full draft set against the 5-point checklist. Revise,
merge, split-flag, or remove epics that fail. Do not include this
scratchpad in the response.

# STEP 5 — EMIT
Return the revised set as `epics.json`. Anything unresolved becomes
an `open_questions` entry, never a best-guess epic.
Why the internal steps are hidden from output: the grounding/reflection scratchpad is reasoning scaffolding, not a deliverable — exposing it would violate the structured-output contract (NFR-G3) and give downstream agents two competing sources of truth (the scratchpad vs. the final JSON) to reconcile.

8. Guardrails (applied at release, after emit)

gr-L1-schema-validator

Structural check against epics.schema.json. Hard block on failure — malformed JSON never reaches downstream agents.

gr-L1-pii-detection

Scans descriptions/business_value for PII patterns. Overlaps with reflection checklist item 5 by design — defense in depth, not redundancy to remove.

gr-L1-hallucination-check

Verifies every source_refs entry actually resolves to real content in the cited roadmap/vision doc. This is the guardrail that catches a grounding-rule failure the agent itself missed.

gr-L2-payments-compliance

If any epic touches payment flows, checks against payments-domain compliance rules before release. Org-specific overlay on top of the generic checks.

9. Quality Gate — epic-quality ≥7

Scored independently by A12 Verifier (fresh context, no access to this agent's scratchpad — see A12 design). Rubric:

CriterionWeightFloorWhat a 10 looks like
Grounding — every field traces to a real source25%6Every source_refs entry resolves; no epic invents scope
Coverage — roadmap fully represented20%—No roadmap line item is missing an epic
No duplication — internally and vs. existing Jira epics20%—dedupe_check ran and found no unresolved overlaps
Scope discipline — one epic ≈ one roadmap phase20%5No epic spans multiple phases without an explicit split flag
Clarity — title/description are specific and actionable15%—A downstream engineer could scope work from the description alone

Failing the gate routes back to this agent for revision (max 2 retries, exponential backoff, NFR-G7) before escalating to the Product Lead HITL gate.

10. Human-in-the-Loop

This is one of the 4 explicit human gates in the lifecycle (Vision → Roadmap → Design → Code review). The Product Lead reviews the emitted epics.json — specifically open_questions and any gate-failure history — before Feature decomposition (A2) is authorized to run. Design implication: open_questions must be written for a human reader, not as an internal debug artifact — plain language, one per line, referencing the ambiguous roadmap/vision content directly.

11. Error Handling & Edge Cases

ScenarioBehavior
Roadmap not yet Product-Lead approvedReject immediately with structured error; do not generate anything
Roadmap references a capability absent from visionEmit an open_questions entry; do not invent a business_value to fill the gap
Jira fetch tool times out / errorsProceed but set dedupe_check.checked=false; this degrades the gate score on the "no duplication" criterion rather than blocking silently
Roadmap is unusually large (50+ line items)Batch internally by roadmap phase; reflection checklist runs per-batch AND once over the full set for cross-batch duplication
Vision and roadmap are from different, incompatible schema versionsHard fail with a versioning error — do not attempt best-effort parsing

12. Non-Functional Requirements

  • Statelessness (NFR-G2): no memory of prior runs beyond the current roadmap/vision pair and the live Jira fetch — re-running against the same inputs should be idempotent modulo Jira state drift.
  • Structured output only (NFR-G3): no prose wrapper, ever, even on partial failure — errors are also structured JSON.
  • Fail loud on missing input (NFR-G4): never silently substitute a default for a required precondition.
  • Grounding (NFR-G5): covered above — this is the agent's defining NFR.
  • Retry/backoff (NFR-G7): max 2 retries on gate failure before HITL escalation.
  • Latency budget: should complete well within the Inception-phase SLA even for large roadmaps — batching (see edge cases) exists partly for this reason.

13. Observability & Audit

  • Correlation ID propagated from Idea intake, attached to every emitted epic and every tool call.
  • Events emitted: step.epic-creator.started, step.epic-creator.quality_gate.pass/fail, step.epic-creator.completed.
  • On gate failure, a Jira subtask is auto-created recording the failed criteria and routing to the Product Lead per the HITL logging convention.
  • reflection_notes (internal) should still be logged to the audit trail even though stripped from the returned JSON — useful for debugging why an epic was merged or dropped, without polluting the output contract.

14. Versioning & Change Management

  • epics.schema.json is versioned independently of the agent prompt; A2 (Feature Decomposer) must declare which schema version it consumes so the two can evolve without breaking each other silently.
  • Rubric changes to epic-quality gate are versioned in kb-L1-sdlc-templates and stamped on every gate result, so historical gate outcomes remain interpretable after a rubric update.
  • Prompt changes should be evaluated against the regression suite (below) before rollout — grounding/reflection wording is easy to accidentally weaken with a small edit.

15. Testing & Eval Strategy

Test typeWhat it catches

Dedupe tests (seed Jira with near-duplicate epics)Whether the Jira fetch-and-compare step actually catches overlap
